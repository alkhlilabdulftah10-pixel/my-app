## المرحلة 1 — التخطيط: حدّد المشكلة قبل الكود

- **شنو المشكلة؟** مطاعم وكافيهات راينه (Rheine) تدفع عمولة عالية (Lieferando/Uber Eats ‏~30%)، أو ما عندها منيو رقمي أصلاً.
- **منو المستخدم؟**
  - الزبون: سكان راينه وضواحيها (عرب، أتراك، ألمان) يبون يتصفحون ويطلبون بسرعة.
  - صاحب المطعم: يبي طلبات بدون عمولة وبدون نظام معقد.
  - الأدمن (أنت): يضيف المطاعم والأطباق.
- **شنو الهدف؟** منصة مركزية واحدة لكل مطاعم راينه، الطلب يروح مباشرة لواتساب المطعم،
  اشتراك شهري ثابت بدل العمولة. البداية بمطعمين تجريبيين.

## المرحلة 3 — التصميم: الواجهة والبيانات والهيكلة

```
UI (React pages)            API (Floot endpoints)            DB (Postgres)
/                       →   GET  /_api/restaurants       →   restaurants
/restaurant/:id         →   GET  /_api/restaurant        →   menu_items (FK → restaurants, ON DELETE CASCADE)
/admin, /admin/:id      →   POST restaurant_upsert/delete →  users / sessions / user_passwords
/login                  →   POST auth/*
                            ↓
                    wa.me/<رقم المطعم>?text=<الطلب>   ← الطلب ما ينحفظ في DB، يروح واتساب مباشرة
```

- التصميم البصري: أبيض، نص شبه أسود، لون واحد "Bestello Blue" للأزرار والأسعار، عناصر بيضاوية (pill).
- ملاحظة مهمة: التطبيق منشور كتطبيق موبايل، فأي تغيير في الـ API لازم يبقى متوافق مع النسخة القديمة.

   - الاسم ≥ حرفين، الهاتف ≥ 6 أرقام (إجباري).
   - العنوان إجباري **للتوصيل فقط**.
   - ملاحظة اختيارية.
   - بيانات الزبون تنحفظ على جهازه للطلب الجاي (بدون الملاحظة).
3. **التصميم**: زر "Per WhatsApp bestellen" يفتح نافذة `CheckoutDialog`، والبيانات تنضاف لرسالة
   واتساب. **بدون أي تغيير في الـ API أو قاعدة البيانات**، فالتطبيق القديم على الجوال يبقى شغال.
4. **التنفيذ** (Floot checkpoint: "v1.2: نموذج الاسم والعنوان والتوصيل قبل طلب واتساب"):
   - `components/CheckoutDialog.tsx` (جديد): `CheckoutDialog` + `CheckoutForm`.
   - `helpers/buildWhatsappOrderUrl.tsx`: معامل `customer` اختياري (متوافق مع الاستخدام القديم).
   - `pages/restaurant.$restaurantId.tsx`: الزر يفتح النموذج بدل الرابط المباشر.
5. **الاختبار**: 13 اختبار ناجح، و typecheck: clean.

## دورة v1.3 — الحد الأدنى للطلب

1. **التخطيط**: الحد الأدنى كان نص فقط ("ab 12 €")، فالزبون يقدر يطلب بـ 3 € والمطعم يرفض.
2. **التحليل**:
   - رقم لكل مطعم.
   - زر الطلب معطّل تحت الحد، مع رسالة "Noch X € bis zum Mindestbestellwert".
   - الأدمن يدخل رقم.
   - تطبيق الجوال القديم ما ينكسر.
3. **التصميم**:
   - عمود `min_order_amount numeric(10,2) NOT NULL DEFAULT 0 CHECK (>= 0)`، تعبّى من النص القديم
     (Al Noor = 12، Istanbul Lezzet = 10).
   - النص `minOrder` يبقى ويتولّد تلقائياً من الرقم، والعكس صحيح: لو أرسل التطبيق القديم نص،
     الرقم ينحسب منه (`helpers/resolveMinOrder`).
   - الـ API: حقل جديد في القراءة + حقل اختياري في الحفظ. ما انحذف شي.
4. **التنفيذ** (Floot checkpoint: "v1.3: فرض الحد الأدنى للطلب"):
   - `helpers/getMinOrderStatus.tsx`: كم باقي؟ (بالسنت، عشان ما تصير أخطاء تقريب).
   - `helpers/resolveMinOrder.tsx`: مزامنة الرقم والنص.
   - `endpoints/restaurant(s)_GET.ts`، `restaurant_upsert_POST(.schema).ts`.
   - `pages/restaurant.$restaurantId.tsx`: الحد يظهر بالهيدر، والزر يتعطّل تحت الحد.
   - `pages/admin.tsx`: حقل رقمي بدل النص.
5. **الاختبار**: 24 اختبار ناجح، و typecheck: clean.
   - `getMinOrderStatus.spec`: تحت الحد، على الحد بالضبط، 3 × 4.10 = 12.30 (أخطاء التقريب)،
     بدون حد، وقيمة غير صالحة.
   - `resolveMinOrder.spec`: رقم صحيح، سنتات بفاصلة ألمانية، الرقم يغلب النص، نص من التطبيق
     القديم، نص بدون رقم، تحديث جزئي.
   - فحص الـ API على سيرفر التطوير: `minOrderAmount` يرجع (12.00 / 10.00)، و `minOrder` القديم
     موجود، والحفظ بدون تسجيل دخول ← 401.
6. **النشر**: ✅ جربه صاحب المشروع في المعاينة، وبعدها انتشر على الويب (bestello.floot.app).
7. **الصيانة**: التالي المقترح: ساعات العمل ← ثلاث لغات ← صور.

## دورة v1.4 — ساعات العمل (🚧 قيد التنفيذ، توقفنا عند حد Floot اليومي)

1. **التخطيط**: الزبون يقدر يطلب من مطعم مسكّر، والطلب يضيع.
2. **التحليل**:
   - ساعات لكل يوم، وأي يوم ممكن يكون عطلة.
   - ساعات بعد منتصف الليل (مثلاً 18:00–01:00).
   - الوقت دايماً بتوقيت ألمانيا (Europe/Berlin)، بغض النظر عن جوال الزبون.
   - "Geöffnet · bis 23:00" أو "Geschlossen · öffnet Di 12:00".
   - زر الطلب يتعطّل والمطعم مسكّر.
   - شارة على الصفحة الرئيسية.
   - الأدمن يعدّل الساعات.
   - مطعم بدون ساعات = مفتوح دايماً (عشان ما ينكسر شي موجود).
3. **التصميم**:
   - جدول `opening_hours` (restaurant_id, weekday 1–7, opens_at, closes_at, UNIQUE(restaurant_id, weekday)).
     - إذا `closes_at <= opens_at` فالفترة تعدّي منتصف الليل.
     - يوم بدون سطر = عطلة.
   - الـ API:
     - `openingHours` يتضاف لـ `restaurant_GET` و `restaurants_GET`.
     - endpoint جديد للأدمن `opening_hours_set_POST`.
4. **التنفيذ**: الحالة بالتفصيل:
   - ✅ الجدول + بيانات تجريبية:
     - Al Noor: كل يوم 11–23، والجمعة والسبت لين 01:00.
     - Istanbul Lezzet: الاثنين عطلة، وباقي الأيام 12–22.
   - ✅ `helpers/getOpenStatus.tsx` (+ `isToday` في `nextOpen`).
   - ✅ `restaurant_GET` / `restaurants_GET` ترجع `openingHours`.
   - ✅ `endpoints/opening_hours_set_POST` (أدمن فقط، transaction) + `useSetOpeningHours`.
   - ✅ `components/OpenStatusLabel` (css جاهز).
   - ⏳ الباقي:
     1. تحديث 3 توقعات في `getOpenStatus.spec.tsx` بإضافة `isToday: false`.
     2. `OpenStatusLabel.tsx`: يستخدم `nextOpen.isToday` بدل `todayWeekday`.
     3. صفحة المطعم: الحالة بالهيدر، تحديث كل دقيقة، تعطيل الزر، ومنع الإرسال لو تسكّر المطعم والنموذج مفتوح.
     4. الصفحة الرئيسية: الحالة على كل بطاقة.
     5. صفحة `/admin/:id`: قسم "Öffnungszeiten" (7 أيام: مفتوح/مسكّر + من/إلى).
     6. الاختبارات + typecheck + فحص الـ API، ثم checkpoint ← تجربتك ← النشر.
5. **الاختبار** (حتى الآن): 14 اختبار لـ `getOpenStatus` ناجحة (قبل إضافة `isToday`):
   - ساعات عادية.
   - لحظة الفتح والإغلاق بالضبط.
   - قبل الفتح وبعد الإغلاق.
   - بعد منتصف الليل (الجمعة والسبت).
   - يوم العطلة، ولفّة الأسبوع (من الأحد للثلاثاء).
   - توقيت ألمانيا مقابل UTC، والتوقيت الصيفي.
   - بدون ساعات = مفتوح.
6. **النشر**: لم يبدأ. النسخة المنشورة ما تأثرت (الجدول الجديد ما تقرأه).
